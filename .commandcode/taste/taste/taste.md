# Taste
- When reporting a bug, expects a fast, direct fix with minimal deliberation (repeatedly ends bug reports with "fast" and escalates to "stop wasting my time" when fixes don't land); prefers the agent to jump straight to the root cause and deliver, rather than long explanations or multi-step back-and-forth. Confidence: 0.85
- Prefers React + Tailwind CSS for frontend builds; explicitly specifies the stack and leaves bundler decisions (Vite vs Next.js) to the agent. Confidence: 0.75
- Wants prototype/demo work to function end-to-end against mocked backend responses so the demo looks complete before real models or services are wired in. Confidence: 0.85
- Wants placeholder pages and mock data to be explicitly labeled as placeholders/mocks (e.g., "static/mock for now") rather than passed off as real functionality. Confidence: 0.6
- Prefers project documentation as a root README covering what the project is and how to set up/run both frontend and backend, plus separate READMEs inside each major component directory. Confidence: 0.7
- Expects the design system to be built on semantic theme tokens (CSS variables mapped through Tailwind config) rather than hard-coded hex/utility colors scattered through components. Confidence: 0.7
- Wants theme preference (light/dark) persisted in localStorage and a toggle exposed consistently across all entry surfaces (landing, auth, and main app). Confidence: 0.7
- Prefers conversation history to be user-specific and role-aware where identity determines whose conversations are visible and role determines what is accessible (private conversation owned by user vs governed task shared for review) with principle Authentication → Authorization → Conversation ownership → Task-level controlled sharing. Confidence: 0.95
- Requires RBAC to be enforced server-side via authenticated user_id-filtered queries (e.g., GET /conversations filtered by user_id) rather than frontend-only conditional rendering, including for tasks, artifacts, and approvals; explicitly rejects frontend-only UI security. Confidence: 0.95
- Prefers agent orchestrator to be conversation-aware, threading prior messages and attached files (e.g., images) into model context so follow-ups like "What about the left side?" retain prior image + history. Confidence: 0.85
- Prefers explicit relational schema for history: users, conversations (user_id, title, timestamps), messages (conversation_id, role, content), attachments (conversation_id, message_id, file_path/type), tasks (conversation_id, user_id, status), and task_access/approvals for governed sharing. Confidence: 0.85
- Treats conversation continuity, user-specific history, RBAC, and task/approval access as a single architecture to be designed together upfront rather than bolting history onto chat later. Confidence: 0.9
- Prefers agent to stop immediately after code implementation without extra run/test/build verification when explicitly told to stop ("no need to run & test, if code implemented stop"). Confidence: 0.75
- Prefers RAG ingestion/retrieval to guarantee contextual integrity, not just data retention — distinguishes "nothing discarded" from "nothing separated from what makes it meaningful"; expects table-aware splitting that detects Markdown tables and re-injects header + separator + preamble into every fragment so no data row is orphaned, and views char-count as a crude proxy for tokenization. Confidence: 0.85
- Prefers small-to-big (parent-section) retrieval as the primary structural pattern for RAG — matching/embedding on small precise chunks but storing and returning the full parent section to the LLM/UI (deduped by section) — explicitly ranked above table-aware splitting (defense-in-depth for huge tables) and token-based sizing (deferred nice-to-have). Confidence: 0.88
- Expects RAG fixes to be verified end-to-end by re-ingesting a real document (e.g., storage tank SOP) and inspecting the raw `excerpt`/`content` field in retrieval (e.g., `knowledge.completed` event) to confirm the complete section/table reaches the model, not a truncated preview or header-less fragment. Confidence: 0.78
- Prefers analysis-before-implementation workflow: wants structured functional + design analysis in the same format as prior feature analyses (e.g., conversations) before any code is written, and explicitly expects the agent not to implement until told to do so. Confidence: 0.88
- Expects immediate, clean revert of unwanted implementations when instructed to revert, with verification that no traces (e.g., role_override/manual routing) remain. Confidence: 0.85
- Expects conversation history to be injected as proper role-tagged ChatML turns (user/assistant pairs) spliced before the current user message outside the system block, not as flattened bullet prose inside the system preamble; expects vision/extraction prompts to share the same treatment. Confidence: 0.85
- Prefers RAG retrieval to be history-aware — expanding the embedding query with prior user turn(s) (simple concatenation or query-rewrite) so bare follow-ups like 'now for shell course 1' retrieve the correct chunks; expanded query is internal to vector search and never shown to model/user. Confidence: 0.82
- Prefers diagnostic-first verification for multi-turn conversational bugs: log/inspect the exact final prompt/messages object right before call_model on the second turn and confirm conversation_id/activeConversationId is present in the second /chat/stream request (network tab) before touching code, to isolate prompt-assembly vs retrieval vs frontend-state failures. Confidence: 0.78
